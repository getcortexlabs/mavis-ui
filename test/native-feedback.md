# Progress and Alert native review

Issues: [#107](https://github.com/getcortexlabs/mavis-ui/issues/107), [#108](https://github.com/getcortexlabs/mavis-ui/issues/108).

Build the packages, install the catalog dependencies, then run `ns build ios --env.production` or `ns build android --env.production` from `examples/catalog`. Use dedicated devices. Both components are in the Composition group. `--env.identityCheck=progress` or `--env.identityCheck=alert` opens a demo directly for isolated checks; use a normal build for catalog/back-navigation checks.

1. In Progress, choose **Zerar**, then **Avançar** through 100%. The fill must be empty at zero and reach the end at 100%; the accessible value must follow the visible percentage. The three samples below use heights 4, 8 and 12 DIP.
2. Enable **Progresso indeterminado**. The accessible value changes to **Preparando**, the manual controls disable, and a 32% segment moves within the track. Rotate and return to portrait; the segment must remain bounded. Disable the mode: the previous known value returns.
3. Hide and show the indicator, navigate back and reopen it, then send the app Home and resume. Motion should resume only on the mounted, loaded indicator. System reduced motion keeps the segment centered with no loop. The unit lifecycle suite checks zero width, resize, mode changes, suspension, preference changes, unload/reload and disposal of subscriptions and pending starts.
4. In Alert, select every tone, use **Ver detalhes**, close and reopen the notice. The action increments the counter; close only changes the demo's visibility state. The separate static notice remains present. Repeat in Midnight and with larger system text. The message wraps, the surface grows and its actions remain reachable by scrolling. Check the rounded outline on Android as well as iOS.
5. Enable **Anunciar atualizações** and change the message. Inspect the title/description group and the separate action/close controls. Automated tests check announcement scheduling and cleanup; actual speech requires a screen reader and is not established by an accessibility-tree dump.
6. In Showcase → Library, choose **Baixar coleção**. Preparation changes to known progress, then a success notice. Exercise **Simular falha**, **Tentar novamente**, **Cancelar download**, notice dismissal and **Ver salvos**. Filters, bookmarks and the tab state belong to Library and survive these operations. Navigate away during a pending timer and reopen the screen. No files are transferred or stored.

Local validation uses the iPhone 17 simulator with iOS 26.2 and a Pixel 7 emulator with Android API 36. Text-size smoke checks use iOS extra-extra-extra-large and Android font scale 1.5; settings are restored afterward. Screenshots and UI trees are kept in ignored `artifacts/feedback`. Browser coverage exercises 320/390/1440 layouts, both themes, animation bounds, reduced motion, hidden tabs, all notice tones, dismissal and the Library workflow. Physical hardware, a complete screen-reader audit and long-running/performance workloads are outside this delivery.
